# ReArc macOS branding and signing

Wave 14 uses Chromium's selected build-time BRANDING file. For the supported
unbranded overlay build, `chrome/app/theme/chromium/BRANDING` selects
PRODUCT_SHORTNAME=ReArc and MAC_BUNDLE_ID=com.rearc.browser. A generated
os_crypt keychain_branding.h derives the unbranded Safe Storage service from
PRODUCT_SHORTNAME plus ` Safe Storage`, and the account from PRODUCT_SHORTNAME.
The resulting names are **ReArc Safe Storage / ReArc**. No ReArc name is
hardcoded in os_crypt; encryption, authorization and error behavior are unchanged.
Google-branded builds retain their existing Chrome keychain constants.

This is a minimal branding overlay. PRODUCT_FULLNAME stays Chromium to preserve
the current framework/executable/helper layout, link names and build script.
Icons, installers, localized strings, updater integration and a full executable
rename are not claimed. The host-facing shell can be packaged as ReArc.app, but
must preserve the engine framework and helper executable names and relative
paths generated by this build. Do not rename nested executables independently.

Production packaging must supply:

- A stable Developer ID Application identity and its actual ten-character Apple
  Team ID. MAC_TEAM_ID is deliberately empty in the development BRANDING file;
  replace it in a release-specific BRANDING input and select that input using
  Chromium's `branding_file_path` GN argument before building. No Team ID or
  signing certificate can be inferred or manufactured by this overlay.
- A reverse-DNS application bundle ID owned by the distributor. The overlay
  default is com.rearc.browser. Use the same selected MAC_BUNDLE_ID for the
  outer Swift app and engine-generated assumptions. If the production ID
  differs, rebuild the engine from that BRANDING input; editing only the
  outer Info.plist creates inconsistent rendezvous/entitlement assumptions.
- Generated helper IDs rooted at the app ID. At this pin the default, GPU,
  Aperitif and Aperitif GPU helpers use `<app>.helper`; renderer and Aperitif
  renderer use `<app>.helper.renderer`; alerts and Aperitif alerts use
  `<app>.framework.AlertNotificationService` (the notification plist generator
  overrides the ordinary helper suffix). These shared IDs are Chromium's intentional templates;
  do not invent eight distinct IDs without auditing its launch/signing code.
  Keep each helper's generated Info.plist, LSUIElement and role-specific
  entitlements, including renderer JIT capabilities.
- Matching Team ID, designated signing requirements and required keychain
  access authorization for the executable that actually accesses Safe Storage.
  Sign nested frameworks/libraries/helpers before the outer application, with
  their Chromium role-specific entitlements and hardened-runtime settings.
  Sign the final executable contents; replacing an executable after signing
  invalidates that signature. Package the entire dependency closure for a
  component dev build; production must separately validate the optimized
  non-component build, notarization and launch on a clean machine.
- A dedicated ReArc user-data directory supplied before engine startup. A
  stable code identity and OS authorization are still required: renaming the
  keychain item does not grant access or prove first-load authorization works.
  Never ship --use-mock-keychain or the stress interposer.

The new Safe Storage names identify a new keychain item. Existing development
profiles encrypted using Chromium Safe Storage cannot be assumed to decrypt
with the new key. Use fresh profiles for verification. A product migration
would require an explicit, separately authorized migration of old encrypted
state/key access; no insecure fallback or silent old-keychain lookup is added.

Validation records generated bundle IDs, generated keychain constants and the
compiled keychain-name implementation, plus the regular runtime gates. The dev
build remains unsigned/ad-hoc; no production signing, keychain ACL, notarization
or distribution authorization result is implied.

The current build.sh deliberately regenerates a fixed development GN argument
set. A production pipeline must supply branding_file_path in its own complete
GN configuration (or prepare the selected default BRANDING as a reproducible
release input); pre-running GN with an override and then running this development
build.sh would overwrite that override. No signing credential is stored here.
The framework ID is `<app>.framework`.

Wave 16's ABI 1.13 `profile_directory` / ReArcProfileOpenDirectory("Default",…)
can assign the existing startup directory to a host profile without relocating
its databases. The host persists that directory mapping rather than creating a
new named directory. This solves storage placement adoption; it does not change
or convert encryption keys. Use the same authorized Safe Storage key as the
stored data. Keep an offline backup before any separately authorized pre-wave-14
key-brand migration. No silent lookup of the old Chromium key is added.

Release packaging (optimized non-component engine, hardened-runtime nested signing,
DMG, notarization prerequisites and versioning) is in RELEASE.md. Its release BRANDING
input sets MAC_TEAM_ID=<TEAM_ID> through `branding_file_path`, as required above.
